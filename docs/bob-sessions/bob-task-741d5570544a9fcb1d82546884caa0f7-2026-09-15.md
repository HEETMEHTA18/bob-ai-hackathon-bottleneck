# # Security Remediation Task

You are working directly on an existing web application codebase.

A security audit has identified the vulnerabilities listed below. Your job is to **remediate the vulnerabilities in the existing project without breaking existing functionality, APIs, UI behavior, data flows, or application architecture unnecessarily.**

## Critical Rule

**DO NOT rewrite the application.**

Make the **smallest, safest, production-quality changes necessary** to remediate the security findings.

Before changing anything:

1. Inspect the existing implementation and understand its architecture.
2. Trace the affected data flow.
3. Identify existing authentication, authorization, middleware, models, configuration, and frontend behavior.
4. Preserve existing functionality wherever possible.
5. Reuse existing utilities/models/dependencies when appropriate.
6. Do not introduce unnecessary dependencies.
7. Do not change API contracts unless absolutely required for security.
8. Do not remove functionality simply because it is difficult to secure.

---

# Vulnerabilities To Remediate

## 1. Hardcoded JWT Secret Fallback — CRITICAL

Current problem:

`SECRET_KEY = os.getenv("SECRET_KEY") or "gridshield-dev-secret-key-change-in-production"`

Remediate this safely.

Requirements:

* Never use a known/default JWT signing secret in production.
* Do not expose the secret through the frontend.
* Preserve the existing JWT authentication architecture.
* Fail safely when a required production secret is missing rather than silently using a public fallback.
* Keep development experience usable where appropriate without creating a production security bypass.
* Ensure existing valid production configuration continues working.
* Do not log the actual secret.

---

# 2. JWT Security — CRITICAL

Review and securely harden JWT handling.

Requirements:

* Ensure JWT signatures are properly validated.
* Ensure the configured algorithm cannot be attacker-controlled.
* Preserve the currently intended authentication flow.
* Add appropriate validation for token expiration.
* Add issuer/audience validation if compatible with the existing architecture.
* Prevent privilege escalation through attacker-controlled JWT claims.
* Ensure authorization is based on trusted server-side identity/role information.
* Preserve legitimate login and authenticated API behavior.
* Implement refresh-token invalidation/revocation appropriately without unnecessarily breaking existing sessions.

Do not simply change the JWT library or rewrite authentication.

---

# 3. Broken Authentication / Brute Force — HIGH/CRITICAL

Secure:

* `/auth/login`
* `/auth/signup`
* password/reset/OTP-related authentication flows if present.

Requirements:

* Add appropriate protection against repeated authentication attempts.
* Ensure rate limiting works correctly across production workers/processes where practical.
* Avoid creating a denial-of-service vulnerability through overly aggressive limits.
* Preserve legitimate users' ability to authenticate.
* Avoid revealing whether an account exists through unnecessarily distinguishable authentication responses.
* Preserve existing API response structure wherever possible.

---

# 4. Refresh Token Revocation — HIGH

The existing refresh-token flow issues new tokens without revoking the previous refresh token.

Implement a secure revocation strategy compatible with the current architecture.

Requirements:

* Prevent indefinite refresh-token reuse.
* Support token rotation.
* Detect/reject reuse of invalidated refresh tokens.
* Preserve normal login → refresh → authenticated-session behavior.
* Do not invalidate legitimate sessions unexpectedly unless required by the security model.

If persistent storage already exists, prefer using the existing database rather than introducing another storage system.

---

# 5. IDOR / BOLA — HIGH

GridShield endpoints currently expose global fleet data to authenticated users.

Review every affected `/api/gs/*` endpoint.

Requirements:

* Enforce object-level authorization.
* Enforce role/ownership/tenant boundaries according to the application's intended access model.
* Prevent ordinary users from accessing resources belonging to other users/tenants/sites.
* Ensure WebSocket subscriptions enforce the same authorization rules as HTTP endpoints.
* Do not rely on frontend restrictions for authorization.
* Keep administrator access working.
* Use the existing `require_admin()` or existing authorization architecture where appropriate.
* Do not accidentally block legitimate administrative functionality.

For every GridShield endpoint, verify:

`authenticated → authorized for this resource → allowed`

not merely:

`authenticated → allowed`

---

# 6. Broken Authorization — HIGH

Audit all privileged GridShield operations.

Requirements:

* Ensure role checks are actually enforced server-side.
* Ensure viewer/normal users cannot access administrative functionality.
* Ensure authorization is applied consistently to:

  * REST endpoints
  * WebSockets
  * resource access
  * configuration operations
  * sensitive data
  * administrative operations.

Do not rely on hidden frontend buttons or UI restrictions.

---

# 7. Path Traversal — POTENTIAL

Review:

`backend/main.py:161-168`

The SPA/static-file catch-all must not allow user-controlled paths to escape `FRONTEND_DIST`.

Requirements:

* Canonicalize/resolve the requested path safely.
* Ensure the resolved path remains inside the intended frontend directory.
* Preserve normal SPA routing and static asset serving.
* Do not break legitimate frontend routes.
* Handle nonexistent files normally.

---

# 8. SSRF — POTENTIAL

Review hardware configuration handling.

Requirements:

* Do not allow arbitrary attacker-controlled network destinations to become trusted server-side connection targets.
* Validate hardware connection configuration according to the application's intended device/network model.
* Since the current implementation uses simulated hardware, do not introduce unnecessary network functionality.
* Ensure future hardware integration cannot accidentally inherit unrestricted attacker-controlled outbound requests.

Do not break the existing simulated hardware behavior.

---

# 9. Mass Assignment — POTENTIAL

Review endpoints such as:

`PUT /assets/{id}/hardware`

and:

`POST /assets/{id}/crew/assign`

Requirements:

* Replace unsafe unrestricted dictionaries with explicit validated schemas where appropriate.
* Allow only fields that are intentionally user-modifiable.
* Prevent modification of internal/security-sensitive fields.
* Preserve the existing valid request format as much as reasonably possible.
* Do not break existing frontend functionality.

---

# 10. Security Misconfiguration — HIGH

Remediate:

* frontend exposure of `SECRET_KEY`
* database configuration exposure
* unnecessary server configuration exposure
* hardcoded demo credentials
* weak CSP.

Requirements:

### Secrets

Never expose:

* JWT secrets
* API keys
* database credentials
* private configuration

to the frontend.

### Demo credentials

Remove hardcoded real/default credentials from production-facing frontend code.

If the application intentionally supports a demo mode, preserve that functionality through a safe mechanism that does not expose production credentials.

### CSP

Strengthen the Content Security Policy.

Remove unnecessary:

* `unsafe-inline`
* `unsafe-eval`

where technically possible.

However:

**Do not break the React application.**

Inspect how the frontend currently uses scripts/styles before changing CSP. Make the smallest compatible change.

---

# 11. Sensitive Data Exposure — HIGH

Review:

* `.env`
* API responses
* logs
* ML status endpoint
* exception handling
* frontend-visible configuration.

Requirements:

* Never expose secrets through API responses.
* Never expose API keys in logs.
* Do not return unnecessary filesystem paths.
* Do not expose internal infrastructure details to ordinary users.
* Do not return stack traces or sensitive exception details to clients.
* Keep useful server-side logging intact without leaking secrets.
* Ensure secrets are sourced from secure server-side configuration.

IMPORTANT:

Do not commit, print, or reproduce real secrets while performing the remediation.

---

# 12. Business Logic Issues — MEDIUM

Review:

`scenario` handling in risk ranking/dashboard APIs.

Requirements:

* Validate attacker-controlled query parameters using the application's intended enum/schema.
* Prevent arbitrary cache-key creation.
* Prevent cache manipulation/resource exhaustion.
* Preserve all legitimate scenario values.
* Ensure response behavior remains compatible with the frontend.

Also review the application for other obvious cases where security-sensitive values are trusted directly from the client.

Server-side business rules must remain authoritative.

# 13. Rate Limiting — HIGH

Requirements:

* Ensure authentication endpoints have appropriate stricter protection.
* Ensure WebSocket connections cannot bypass security controls.

* Correctly handle reverse-proxy deployments without treating every user as the same client when trusted proxy configuration is available.
* Do not introduce excessive rate limits that break normal application usage.
* Preserve existing legitimate traffic.

Do not blindly replace the entire middleware.

* its callers

* frontend expectations
* database schema

* WebSocket behavior

Where possible:

* preserve endpoint URLs
* preserve HTTP methods
* preserve response schemas
* preserve existing frontend behavior
* preserve database compatibility
* preserve existing authentication UX.

* stack traces
* database errors
* filesystem paths
* secrets
* internal implementation details.

But keep useful diagnostic information in server-side logs.

## Dependencies

1. Check whether an existing dependency already provides the required functionality.
2. Prefer the existing project stack.
3. Add a dependency only when genuinely necessary.

async def _revoke_token_jti(db: AsyncSession, jti: str, user_id: str, expires_at: datetime) -> None:
    """Persist a refresh-token JTI so it cannot be reused."""
    entry = RevokedToken(jti=jti, user_id=user_id, expires_at=expires_at)

async def _is_jti_revoked(db: AsyncSession, jti: str) -> bool:
    result = await db.execute(select(RevokedToken).where(RevokedToken.jti == jti))
    return result.scalar_one_or_none() is not None

@router.post("/refresh", response_model=TokenResponse)
async def refresh_token(data: TokenRefresh, db: AsyncSession = Depends(get_db)):
    payload = decode_token(data.refresh_token)
    if not payload or payload.get("type") != "refresh":
        raise HTTPException(status_code=401, detail="Invalid refresh token")

    jti = payload.get("jti")
    if not jti:
        raise HTTPException(status_code=401, detail="Invalid refresh token")

    # Reject if this JTI has already been revoked (replay detection)
    if await _is_jti_revoked(db, jti):
        raise HTTPException(status_code=401, detail="Refresh token has been revoked")

    user_id = payload.get("sub")
    result = await db.execute(select(User).where(User.id == user_id))
    user = result.scalar_one_or_none()

    if not user:
        raise HTTPException(status_code=401, detail="User not found")

    if not user.is_active:
        raise HTTPException(status_code=403, detail="Account disabled")

    # Token rotation: revoke the consumed token before issuing a new one
    exp_ts = payload.get("exp")
    expires_at = datetime.utcfromtimestamp(exp_ts) if exp_ts else datetime.utcnow()
    await _revoke_token_jti(db, jti, str(user.id), expires_at)

    access_token = create_access_token({"sub": str(user.id), "role": user.role})
    new_refresh_token, _new_jti = create_refresh_token({"sub": str(user.id)})

    return TokenResponse(
        access_token=access_token,
        refresh_token=new_refresh_token,
        user=UserResponse.model_validate(user),
    )


@router.post("/logout")
async def logout(data: TokenRefresh, db: AsyncSession = Depends(get_db)):
    """Revoke the supplied refresh token immediately."""
    payload = decode_token(data.refresh_token)
    if payload and payload.get("type") == "refresh":
        jti = payload.get("jti")
        if jti and not await _is_jti_revoked(db, jti):
            user_id = payload.get("sub", "")
            exp_ts = payload.get("exp")
            expires_at = datetime.utcfromtimestamp(exp_ts) if exp_ts else datetime.utcnow()
            await _revoke_token_jti(db, jti, user_id, expires_at)
    return {"detail": "Logged out"}

# ─── Rate limiting ─────────────────────────────────────────────────────────────
# Per-IP sliding-window buckets.  Auth endpoints use a much stricter limit to
# mitigate brute-force attacks.  WebSocket connections must authenticate via
# token before the WS upgrade, so the HTTP rate limit covers them too.

_rate_buckets: dict[str, list[float]] = defaultdict(list)
_auth_buckets: dict[str, list[float]] = defaultdict(list)

# Auth endpoints that require the stricter per-minute limit
_AUTH_PATHS = {"/auth/login", "/auth/signup", "/auth/refresh"}


def _get_real_ip(request: Request) -> str:
    """Return client IP, honouring X-Forwarded-For only when a trusted proxy
    is configured (TRUSTED_PROXY env var set to the proxy's IP).  Otherwise
    fall back to the direct connection address to prevent IP spoofing."""
    trusted_proxy = os.environ.get("TRUSTED_PROXY", "").strip()
    if trusted_proxy and request.client and request.client.host == trusted_proxy:
        forwarded_for = request.headers.get("x-forwarded-for", "")
        if forwarded_for:
            # Take the leftmost (original client) address
            return forwarded_for.split(",")[0].strip()
    return request.client.host if request.client else "unknown"


@app.middleware("http")
async def rate_limit_middleware(request: Request, call_next):
    client_ip = _get_real_ip(request)
    now = _time.time()
    window = 60.0
    path = request.url.path

    # Auth endpoints: strict bucket
    if path in _AUTH_PATHS:
        _auth_buckets[client_ip] = [t for t in _auth_buckets[client_ip] if now - t < window]
        if len(_auth_buckets[client_ip]) >= AUTH_RATE_LIMIT_PER_MINUTE:
            remaining_secs = int(window - (now - _auth_buckets[client_ip][0]))
            return JSONResponse(
                status_code=429,
                content={"detail": "Too many authentication attempts. Try again later."},
                headers={"Retry-After": str(remaining_secs)},
            )
        _auth_buckets[client_ip].append(now)

    # General request bucket
    _rate_buckets[client_ip] = [t for t in _rate_buckets[client_ip] if now - t < window]
    if len(_rate_buckets[client_ip]) >= RATE_LIMIT_PER_MINUTE:
        remaining_secs = int(window - (now - _rate_buckets[client_ip][0]))
        return JSONResponse(
            status_code=429,
            content={"detail": "Rate limit exceeded. Try again later."},
            headers={"Retry-After": str(remaining_secs)},
        )
    _rate_buckets[client_ip].append(now)
    response = await call_next(request)
    response.headers["X-RateLimit-Limit"] = str(RATE_LIMIT_PER_MINUTE)
    response.headers["X-RateLimit-Remaining"] = str(max(0, RATE_LIMIT_PER_MINUTE - len(_rate_buckets[client_ip])))
    return response

# Implementation Rules

## Preserve Existing Functionality

Before modifying a component, understand:

* its callers
* request/response formats
* frontend expectations
* database schema
* authentication flow
* WebSocket behavior
* existing tests.

Do not make speculative architectural changes.

## Backward Compatibility

Where possible:

* preserve endpoint URLs
* preserve HTTP methods
* preserve response schemas
* preserve existing frontend behavior
* preserve database compatibility
* preserve existing authentication UX.

If a security fix necessarily changes behavior, make the smallest required change.

## Secrets

Never print secrets.

Never hardcode replacement secrets into source code.

Never commit `.env` secrets.

Use environment/configuration mechanisms already present in the project.

## Error Handling

Security errors should not expose:

* stack traces
* database errors
* filesystem paths
* secrets
* internal implementation details.

But keep useful diagnostic information in server-side logs.

## Dependencies

Before adding a dependency:

1. Check whether an existing dependency already provides the required functionality.
2. Prefer the existing project stack.
3. Add a dependency only when genuinely necessary.
