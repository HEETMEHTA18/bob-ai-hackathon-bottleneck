PHASE 2 — IMPLEMENT SECURITY FIXES
==================================================

Fix the following findings.

--------------------------------------------------
1. HARDCODED JWT SECRET — CRITICAL
--------------------------------------------------

Remove the known JWT secret fallback.

Current problematic behavior:

SECRET_KEY = os.getenv("SECRET_KEY") or "gridshield-dev-secret-key-change-in-production"

Requirements:

- Never use a publicly known JWT signing secret.
- Never expose SECRET_KEY to the frontend.
- Never print the secret.
- Production must require a securely configured secret.
- Development must remain usable through environment configuration.
- Do not hardcode a replacement secret.
- Existing valid SECRET_KEY environment configuration must continue working.

If APP_ENV/development mode already exists, use the existing configuration architecture rather than inventing a new one.

--------------------------------------------------
2. JWT SECURITY — CRITICAL
--------------------------------------------------

Harden JWT handling.

Requirements:

- Algorithm must be server-controlled.
- Signature must always be validated.
- Expiration must be validated.
- Prevent attacker-controlled role/privilege escalation.
- Use trusted server-side user/role information for authorization.
- Add issuer/audience validation only if compatible with the existing architecture.
- Preserve existing login and authenticated API behavior.

Do NOT unnecessarily rewrite the authentication system.

--------------------------------------------------
3. REFRESH TOKEN ROTATION / REVOCATION
--------------------------------------------------

Implement secure refresh-token rotation.

Required behavior:

    Login
      ↓
    refresh token A
      ↓
    refresh using A
      ↓
    refresh token B
      ↓
    refresh using A again
      ↓
    REJECT

Requirements:

- Old refresh token becomes invalid after successful rotation.
- Replayed refresh token must be rejected.
- Logout must invalidate the active refresh token.
- Password/security events should be able to invalidate refresh tokens if the existing architecture supports it.
- Preserve normal refresh behavior.

Prefer existing database/storage mechanisms.

Do not create an unnecessarily complicated token system.

--------------------------------------------------
4. AUTHENTICATION / BRUTE FORCE
--------------------------------------------------

Protect authentication endpoints.

At minimum:

- /auth/login
- /auth/signup
- password reset / OTP endpoints if present

Requirements:

- Failed authentication attempts must be rate limited.
- Authentication rate limits must be stricter than ordinary API traffic.
- Avoid account enumeration through unnecessarily different authentication errors.
- Preserve legitimate login.
- Avoid a global rate limit that causes all users behind one proxy to block each other.

Do not implement an intentionally tiny limit that breaks normal usage.

--------------------------------------------------
5. IDOR / BOLA — HIGH
--------------------------------------------------

Fix GridShield object-level authorization.

Current issue:

Authenticated users can access global fleet data regardless of role/ownership.

Requirements:

- Determine the intended authorization model from the existing code.
- Enforce ownership/tenant/site authorization where applicable.
- Administrative users retain legitimate access.
- Viewer users retain legitimate read access to resources they are authorized to see.
- Users must not access another user's/site's protected resources.
- Authorization must be enforced server-side.

Review ALL GridShield routes, not just one endpoint.

--------------------------------------------------
6. BROKEN AUTHORIZATION — HIGH
--------------------------------------------------

Existing require_admin() must actually be used where administrative privileges are required.

Audit:

- GridShield routes
- configuration endpoints
- hardware endpoints
- ML endpoints
- administrative actions
- sensitive operations

Do NOT blindly put require_admin() on every endpoint.

Determine which operations are actually administrative.

Normal read-only functionality must continue working.

--------------------------------------------------
7. WEBSOCKET AUTHORIZATION — HIGH
--------------------------------------------------

Fix WebSocket authorization.

Current issue:

Any authenticated user can subscribe to arbitrary site_id.

Requirements:

- Authenticate the WebSocket.
- Authorize the requested site_id.
- Prevent access to unauthorized sites.
- Preserve legitimate subscriptions.
- Apply the same authorization model used by HTTP APIs.
- Do not trust site_id merely because the user is authenticated.

Also avoid unnecessarily leaking authentication tokens through URLs/logging.

- Do not break React routing.

Use safe path resolution rather than string-based checks alone.

--------------------------------------------------

Current hardware functionality is simulated.

Do NOT introduce real network functionality.

Instead:

- Restrict host/port fields to the application's intended format.
